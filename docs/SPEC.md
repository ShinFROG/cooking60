# 30日60品の料理学習サイト 仕様案

作成日 2026年10月17日。GitHub Pagesで、30日間の昼食と夕食を異なる60料理で組み、作れる料理を増やすための公開サイトを作る。初版は「30日献立・60品一覧・料理の作り方・買い物・習得記録」を一続きにする。公開教材と利用者の練習記録を分け、個人情報を含まない構成にする。

## 1 依頼で確定していることと仮定

| 区分 | 内容 |
| --- | --- |
| 確定 | GitHubで管理し、GitHub Pagesで公開する |
| 確定 | 30日×昼・夕の60枠に、異なる60料理を用意する |
| 確定 | 朝食は毎日同じでもよい。60料理の集計対象に含めない |
| 確定 | 公開して差し支えない内容だけを整理する |
| 今回の範囲 | 約100サイトの調査と仕様策定。実装・GitHubへの投稿・公開は次の工程 |
| 確定 | 「主食」は昼夕の料理全般。丼・麺・カレー・主菜＋ご飯を含める |
| 確定 | 初心者向け、普段の食材、調理30分以内を中心にする |
| 設計方針 | 日本語、スマートフォン中心 |
| 設計方針 | 1人分を基本に1〜4人へ変更。60品中48品以上を総時間30分以内に収めることを目標とする |
| 未確定 | 食べられない食材、所持器具、予算、GitHub公開先、最終的なライセンス |

60品の範囲と優先条件は依頼者の回答で確認済み。30分は、調理開始から食べられる状態になるまでの総時間として扱う。炊飯済みのご飯を使う料理は、その前提を一覧にも表示する。生米から作る料理は炊飯時間を含める。48品以上という比率は設計目標であり、実測前の達成値ではない。栄養バランスや特定の食事制限への適合を保証する献立ではない。

| 調査で得た視点 | 初版の設計判断 | 主な参照先 |

各サイトの機能説明は設計の参考であり、同じ効果が今回のサイトで得られるという実証ではない。会員登録後の操作、画面の目視評価、全レシピの試作、転載許可の全件確認は今回に含まない。

## 3 60品と習得の数え方

- 1料理に1つの安定した recipeId を付ける。名前の表記揺れ、人数変更、トッピング変更では増やさない。
- 同じ料理の味付け違いは原則同じ料理として扱う。主材料・調理法・完成形が実質的に違うものは、編集時に根拠を書いて別料理にする。
- 同じ主菜にご飯を付けたものと丼にしたものだけで、2品に水増ししない。朝食、副菜、汁物単独、残り物を食べただけの回は60料理に加算しない。
- 標準献立は Day 1〜30 の昼・夕、合計60枠に異なる60IDを1回ずつ割り当てる。
- 日付入りの開始日や実績は利用端末だけに保存する。公開する献立には実際の生活日程を含めない。
- 予定を入れ替える場合、既に入っている料理なら2枠を交換する。重複を作らない。保留・外食も記録できるが未達成のまま扱う。

| 指標 | 判定 |
| --- | --- |
| 初回調理数 | 一度以上「作った」と記録した異なる料理ID数。上限60 |
| 習得数 | 一度以上の調理記録があり、利用者が「主な手順と火加減を説明でき、再度作れる」と自己確認したID数 |
| 30日計画の達成 | 60枠で異なる60料理を実際に作った |
| 習得目標の達成 | 60料理すべてが上記の習得条件を満たした |

30日は献立の長さであり、習得の期限は固定しない。30日計画で全料理を一度作ることと、60料理を習得することは別に表示する。別日にもう一度作る復習を勧めるが、120回の調理を必須条件にはしない。復習は30日を超えて続けられる。初版の完了判定で習得を自動認定しない。記録は編集・取消できる。

## 5 画面と操作の流れ

基本動線は「はじめに → 今日の昼夕 → 料理詳細 → 調理 → 作った記録」。買物は「今週 → 期間・人数 → 買物リスト」。復習は「習得状況 → 再練習する料理 → 調理」に分ける。

| 画面 | 上から表示するもの | 主な操作 |
| --- | --- | --- |
| ホーム | 今日の昼夕、初回調理数と習得数、今週の買物、次の復習 | 作る、予定を見る |
| 30日献立 | 開始日、Day番号、昼、夕、実施状態 | 週へ切替、入替、保留 |
| 60品一覧 | 検索、絞込み、件数、料理カード | 詳細へ、条件解除 |
| 料理詳細 | 名前、学ぶ技術、時間、人数、材料、手順、コツ、出典 | 人数変更、作り始める、記録 |
| 買物 | 期間と人数、朝食を含める選択、売場別材料 | 家にある、購入済、印刷 |
| 習得状況 | 初回と習得の集計、未着手・再練習・習得、個別記録 | 記録編集、データ書出し |
| 出典と方針 | 公開範囲、ライセンス、引用元、保存の説明、変更履歴 | 参照元へ移動 |

スマートフォンでは「今日・献立・料理・買物・記録」の5項目を主ナビゲーションとする。献立は横幅の狭い端末で巨大なカレンダーにせず、日ごとに昼夕を縦に並べる。色だけで状態を表さず、文字ラベルを併記する。操作対象は44px以上を目標とし、キーボードでも入替・チェックできる。料理カードの画像は必須にせず、料理名と判断材料を先に整える。

## 6 料理教材と60品候補

各料理には、料理名、分類、主要材料、人数、実作業時間、総時間、事前準備、道具、学ぶ技術、材料、手順、成功の目印、失敗しやすい点、代替案、試作状態、出典を持たせる。

手順は1項目1作業を基本とし、「適当に炒める」のような表現を避ける。火加減、時間の目安、見た目・手触りなどの到達目印を組み合わせる。炊飯・解凍・漬込みを必要とする場合は、総時間の含め方と事前準備を明示する。30分判定は1人分の初心者試作で確認する。人数変更時は同じ時間内に完成する保証をしない。人数変更で材料は換算するが、加熱時間を機械的に倍増しない。

60品の候補と30日への配置案は CANDIDATES.md、機械可読版は menu-candidates.json にまとめる。候補は料理名と学ぶ技術を新規に編成したもので、完成したレシピではない。現時点では全品未試作。材料量、所要時間、器具条件、食品の保存条件は教材作成時に検証する。

学習の順序は、計量と切り方、炒める・焼く、煮る・とろみ、蒸す・包む、複数工程の段取りへ進む。食材の使い回しは週の献立編集時に整えるが、「同じ食材を使う」と「調理済みの物を数日保存する」を混同しない。

固定朝食は任意で1パターンを選べるようにする。例はトースト・ヨーグルト・果物、またはご飯・納豆・汁物。朝食は料理数に加算せず、材料を買物に含めるかだけ選べる。

食品の取り扱いは[農林水産省の家庭での食中毒予防](https://www.maff.go.jp/j/syouan/seisaku/foodpoisoning/point.html)を基礎資料とする。保存日数や加熱条件は料理ごとに根拠を確認して記載する。初版は材料と加工品の注意を表示し、アレルギー適合の自動判定は行わない。加工品の成分や代用品は商品表示で確認する。苦手食材に応じた候補差替えは教材編成時に行い、アプリでの自動除外・60品の自動再生成は初版に含めない。

## 7 公開できる内容のルール

公開されているページを読めることと、その文章・写真を再利用できることは別として扱う。今回の調査記録はURLと独自の短い観察・設計案だけを保存し、他サイトのレシピ本文、写真、スクリーンショットを収録しない。

| 種類 | 公開物に含める条件 |
| --- | --- |
| 料理名・分類・独自の学習目標 | 公開可。特定サイトの一覧をそのまま再現しない |
| 作り方・説明文 | 独自に作成・試作確認した文章。元記事の近い言換えを教材にしない |
| 写真・図 | 自作、または用途に合う再利用許可を確認した素材。権利不明は使わない |
| 参照リンク | サイト名・URL・確認日・参照目的を記録。リンク先の権利を自サイトへ移さない |
| CC等の素材 | 作者、元URL、ライセンスURL、変更内容、取得日を記録し、条件を満たす |
| 個人の履歴・メモ | リポジトリと配信物には含めない。利用者のブラウザ内に保存 |
| 氏名・住所・連絡先・健康情報 | 標準データ・サンプル・テストデータに入れない |
| 認証情報・内部資料 | 公開リポジトリ、履歴、ビルド成果物に含めない |
| 画像の位置情報 | 自作写真も公開用に書出し、位置情報と私的な写り込みを取り除く |

コードはMIT、独自教材はCC BY 4.0を採用候補とする。これは仕様上の提案であり、この文書の作成だけで利用者の既存資料や第三者素材へライセンスを付与しない。初回公開までに権利者名と適用範囲を確定し、コード・教材・第三者素材を明示する。[GitHubのライセンス説明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)、[Creative Commonsのライセンス一覧](https://creativecommons.org/cc-licenses/)を参照。

素材台帳には contentId、assetPath、author、sourceUrl、license、licenseUrl、modified、checkedAt、rightsStatus を保存する。rightsStatus が未確認の素材はビルドを失敗させる。reference-only のリンクは本文・画像の複製許可として扱わない。

## 8 データ設計

| データ | 主な項目 | 公開範囲 |
| --- | --- | --- |
| Recipe | id、canonicalDishId、title、mealForm、stapleType、ingredientIds、equipmentIds、skillIds、difficulty、baseServings、時間、材料、工程、参照先、試作状態 | 公開 |
| Ingredient | id、標準名、別名、売場分類、単位、状態、換算可能な単位 | 公開 |
| Step | id、説明、火加減、時間目安、成功目印、注意、任意の写真 | 公開 |
| StandardPlan | Day 1〜30、昼recipeId、夕recipeId、学習段階 | 公開 |
| Source / Asset | URL、作者、利用条件、確認日、変更情報 | 公開 |
| PersonalPlan | 開始日、入替、保留、人数、固定朝食設定 | 端末内 |
| Progress | recipeId、調理日、回数、自己確認、再練習、メモ | 端末内 |
| ShoppingState | 対象期間、家にある材料、購入済み、追加項目 | 端末内 |

recipeIdは変更しない。料理名変更後も履歴を引き継ぐ。公開データと個人記録には別のschemaVersionを持たせる。公開データの更新時は参照不能IDを検知し、記録を勝手に削除しない。

買物集計は「同じ食材ID・同じ状態・互換性のある単位」だけを合算する。例として、同じ規格の卵1個＋2個は3個、玉ねぎ100g＋200gは300gになる。玉ねぎ1個と100gは重量の定義がなければ併記する。生米と炊いたご飯、乾麺とゆで麺、缶詰と生魚は区別する。少々・適量は数値化しない。スプーン表記は定義した容量換算だけ行い、食材の密度を無視してgとmLを混ぜない。

初期人数は1人、変更範囲は1〜4人。端数の卵などは元の必要量を保持して調整の注記を付ける。買物でパック数へ切上げる場合も調理量を勝手に増やさない。保留・外食の枠は買物集計から除外する。必要量が増えた行、単位・状態が変わった行は購入済・家にあるチェックを解除し「数量を再確認」と表示する。数量が同じか減った行のチェックは維持し、不要になった行は一覧から外す。例えば購入済みの卵2個が人数変更で4個になった場合は未確認へ戻す。

## 9 GitHub Pagesでの実装構成

HTML・CSS・JavaScriptを静的ファイルとして生成し、GitHub Pagesで配信する。料理データはJSON、画面は共通テンプレートから生成する。初版は大型フレームワークを必須にせず、Node.jsの小さな生成スクリプトとブラウザ標準機能で実装する。

GitHub Pagesは静的サイトの配信サービスで、GitHub Freeでも公開リポジトリで利用できる。標準URLはプロジェクト形式ではアカウント名.github.io/リポジトリ名となる。このためサブパスを前提にリンク・画像・データ取得を生成する。[GitHub Pages公式説明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

| 項目 | 方針 |
| --- | --- |
| ページ生成 | ホーム、一覧、料理ごとのHTML、30日献立、基礎、出典、404 |
| 更新 | JSONの編集 → 検証 → 静的生成 → distへ出力 |
| 検索 | 60件の公開索引をブラウザ内で検索。外部検索API不要 |
| 記録 | localStorage。キーにアプリ名・リポジトリ識別子・スキーマ版を含める |
| ルーティング | 実体のあるHTMLを生成。個別料理URLの直接アクセス・再読込に対応 |
| 配信 | GitHub Actionsで検証・ビルドし、distだけをPagesの成果物にする |
| 公開時の操作 | 実装完了後に対象リポジトリと公開URLを決定し、HTTPSで確認 |
| 外部通信 | 教材表示・記録で外部APIは呼ばない。初版は解析タグと外部フォントなし |
| サイズ | 初版の配信物20MB以内、1料理画像200KB程度を目標。動画は配信しない |

GitHub Actionsの公開手順は[公式の公開元設定](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)に沿う。Actionのバージョンは実装時に公式で確認する。ワークフローはプルリクエストで検証、本番ブランチで配信し、トークンをフロントエンドに埋め込まない。

localStorageは同一オリジン単位で保存され、ブラウザや端末を変えても自動同期されない。保存拒否・容量エラーを扱い、保存できない場合も閲覧とその場の操作は継続できるようにする。記録の書出し・読込みを必須にする。起動時に旧版キーを検知して検証済みの移行処理を行い、成功確認まで旧版を保持する。移行失敗時は旧版を書き換えず、そのまま書出せるようにする。未知の新しい版は上書きしない。[MDNのlocalStorage説明](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)

同じ account.github.io の別リポジトリのサイトは同一オリジンで、保存領域の隔離境界にはならない。キーの識別子は衝突防止のためでありアクセス制限ではない。全削除は本アプリのキーだけを対象にし、localStorage.clear()を使わない。記録は端末内保存だが、同じ端末・ブラウザを使う人からの秘密保管庫ではない。初版は健康情報などの機微な記録を求めない。サイト運営者の独自解析は入れず、GitHub側のセキュリティログは別に扱う。GitHubはPages訪問者のIPアドレスを保安目的で記録すると説明している。[GitHub Pagesのデータ収集](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

提案するリポジトリ内の構成は次のとおり。

- data/public/recipes.json、ingredients.json、plan.json、sources.json
- src/templates/、src/styles/、src/scripts/
- public/assets/、public/404.html
- scripts/build.mjs、scripts/validate.mjs
- docs/SPEC.md、docs/RESEARCH.md、docs/CONTENT_POLICY.md
- LICENSE、CONTENT_LICENSE.md、THIRD_PARTY_NOTICES.md、README.md
- .github/workflows/pages.yml
- dist/ は配信物。作業環境全体を成果物にしない

個人記録の出力や試作時の私的メモは、この公開用リポジトリの外に置く。.gitignoreだけを非公開化の手段にせず、公開するファイルを限定して取り込む。既存の作業領域を丸ごと初回コミットしない。
